# RP3 + WS2812B LED Matrix Project — Handoff Report

Status snapshot for whoever picks this up next. Branch: `claude/rp3-led-matrices-gff4ft`.
Everything below is pushed to that branch; nothing is only local.

## What this is

A Raspberry Pi 3 drives two daisy-chained WS2812B ("NeoPixel") LED matrix
panels (WS2812ECO, 32x8 each) to show scrolling text and/or a media
playback queue (images/video), controlled live from a web page served by
the same script. Entirely unrelated to `thermal_matrix.py` / `install.sh`
in this repo, which drive a different Pi's HUB75 panel over a different
library — do not touch those files for this project.

All the code lives in one file: **`media_matrix.py`** (repo root). No
Flask/Django/etc — a hand-rolled `http.server.ThreadingHTTPServer` control
server plus a render loop, sharing a lock-protected `State` object.

## Hardware

- 2x WS2812ECO matrix panels, 32 wide x 8 tall each, daisy-chained
  (Panel 1 DOUT -> Panel 2 DIN).
- Data: Pi GPIO18 (physical pin 12) straight into Panel 1 DIN. **No level
  shifter in the final build** — direct 3.3V GPIO into DIN works fine in
  practice, despite WS2812B nominally wanting ~5V logic. This was
  empirically verified, not a fallback.
- Power: separate 5V/60A supply feeds each panel's own 5V/GND pads
  directly (not through the Pi), fused per panel. All grounds (Pi GND,
  supply GND, both panels' GND) tied together as the signal reference.
- Full wiring diagram (PSU terminal layout, alternate "power the Pi from
  its own supply" variant) was built as a Claude Artifact earlier in this
  project's history — not committed anywhere as a file; ask the user if
  they still have the link, or regenerate from this description if needed.

## Software architecture (`media_matrix.py`)

Single-file, no external framework. Top-to-bottom:

- **`fit_frame`** — shared resize/crop/letterbox helper.
- **`adjust_frame(frame, brightness_pct, contrast_pct)`** — software
  brightness/contrast, percent-based (100 = neutral), layered on top of
  (separate from) the hardware `strip.setBrightness()`.
- **`transform_frame(frame, rotation_deg, scale_pct, offset_x, offset_y)`**
  — *just added*. One affine warp (`cv2.getRotationMatrix2D` +
  `warpAffine`) doing rotation-about-center, scale, and X/Y pixel
  translation for the composited media frame. Short-circuits to a no-op
  when all params are at defaults.
- **`ClipSource`** — per-queue-item decoder (image or video, with
  trim/loop semantics via `start`/`end`/`loop`).
- **`QueuePlayer`** — sequences `ClipSource` items with a smoothstep
  crossfade. `next_frame(dt, canvas_w, out_h, media_brightness,
  media_contrast, media_rotation, media_scale, media_pos_x, media_pos_y)`
  applies per-item brightness/contrast, blends, then applies the global
  brightness/contrast and the new global rotate/scale/position transform,
  in that order.
- **`TextScroller`** — scrolling text. Two independent axes of control:
  - `direction` (`left`/`right`/`up`/`down`) — **purely** which axis the
    content slides on and which way. Nothing to do with rendering.
  - `stacked` (bool) — **purely** how it's drawn: `False` = one normal
    line; `True` = one character per "cell", each optionally rotated in
    place via `glyph_rotate` (0/90/270).

  These two used to be coupled (stacked always meant vertical travel);
  they were deliberately decoupled so any of the 4 combinations works,
  because the "correct" look depends on how the physical panels ended up
  wired/rotated and has to be discovered empirically on the hardware, not
  guessed in code.

  **Bug fixed this session:** in the `stacked` branch, characters were
  always advanced along the *y* axis regardless of travel direction. When
  travel was horizontal, the drawing canvas height was pinned to `out_h`
  (the panel height, e.g. 8px) but characters were still being stacked
  downward by `line_h` each — so all but one character landed outside
  that short window and got clipped, leaving a single stray letter
  visible. Fix: characters now advance along whichever axis is the actual
  travel axis, with the other axis fixed to the panel's cross-section.
  Verified with a pixel-run test confirming 4 distinct, non-overlapping,
  in-order glyphs for both horizontal and vertical stacked travel.

- **`build_index_map`** / **`render_wiring_svg`** / **`render_panel_svg`**
  — SVG wiring diagrams generated by literally tracing the same index-map
  function used for real rendering, so the diagrams can never drift out
  of sync with actual pixel-chain behavior. Per-panel config:
  `{"serpentine", "serpentine_axis", "rotate"}`.
- **`parse_multipart`** — hand-rolled multipart parser for uploads.
  `KIND_BY_EXT` validates file type; `MAX_UPLOAD_BYTES = 200MB`.
- **`Preview`** — thread-safe last-rendered-frame holder, polled by
  `/frame.json` to drive the browser pixel-grid emulator.
- **`State`** — the shared, lock-protected config object. Fields as of
  now: `text, color, bold, italic, scroll_speed, text_direction,
  text_stacked, text_glyph_rotate, brightness, media_brightness,
  media_contrast, media_rotation, media_scale, media_pos_x, media_pos_y,
  layout, panels[], queue[], version`.
  - `snapshot()` — internal form for the render loop (color as RGB tuple).
  - `to_wire()` — JSON-safe form for the web UI / saved config file (color
    as hex, no `version`).
  - `apply_wire(data)` — the single mutation entrypoint for both the web
    UI and a loaded config file. Only bumps `version` (triggers a
    geometry/scroller rebuild) for fields that actually need one
    (text/color/style/layout/panels); brightness/contrast/rotation/scale/
    position are live-applied every frame with no rebuild.
  - **Security invariant, must be preserved:** `apply_wire` can only
    edit/remove queue items whose `id` already exists. New items can
    *only* be created through `/upload` (validated extension, generated
    filename under `--upload-dir`). Never let `/update` fabricate a new
    queue entry.
- **`ControlHandler`** — routes:
  - `GET /` — full control page (HTML+embedded JS).
  - `GET /diagram`, `GET /panel-diagram?i=N` — wiring SVGs.
  - `GET /config.json` — download current config.
  - `GET /autoupdate` — `{"enabled": bool|null}` via `systemctl is-active`.
  - `GET /frame.json` — `{w, h, pixels}` for the live pixel-grid preview.
  - `POST /update` — apply a partial `State` edit (JSON body).
  - `POST /upload` — multipart file upload, appends a queue item.
  - `POST /autoupdate` — `{"enabled": bool}`, enables/disables the
    autoupdate timer via `systemctl enable|disable --now`.
- **`autoupdate_status()` / `set_autoupdate()`** — shell out to
  `systemctl`, wrapped in try/except returning `None`/`False` rather than
  crashing when systemd isn't reachable (relevant in the sandbox; on the
  real Pi it works normally).
- **`main()`** — render loop. `compute_geometry(snap)` derives
  `idx_map, canvas_w, canvas_h, text_h, video_h` live from whether the
  queue/text are non-empty. `rebuild_scroller(snap)` reconstructs
  `TextScroller` when `version` changes. Each tick:
  `player.next_frame(...)` → composite text with sign flip for
  right/down → `preview.update(frame)` → `strip.setBrightness()` →
  per-pixel `strip.setPixelColor()` via `idx_map`.

## CLI flags (`parse_args`)

```
--media PATH              seed first queue item (video)
--text STR                scrolling text
--text-height N           rows reserved for text when video also present (default 4)
--font PATH / --font-size N
--text-color "R,G,B"
--bold / --italic
--scroll-speed PX_S       default 40.0
--text-direction {left,right,up,down}   travel axis, default left
--text-stacked            draw one character per row/column (default off)
--text-glyph-rotate {0,90,270}          rotate each character, only meaningful with --text-stacked
--rotate {0,180}          per-panel seed rotation (startup default for all panels)
--fit {letterbox,fill}
--web-port N              default 8098
--upload-dir PATH
--transition-s N          crossfade duration, default 0.6
--panel-width N / --panel-height N      default 32 / 8
--num-panels N            default 2
--layout {horizontal,vertical}
--serpentine / --no-serpentine          default on
--serpentine-axis {row,column}          default row
--led-pin, --led-freq-hz, --led-dma, --led-invert, --led-channel
--brightness N            0-255, LED hardware level, default 80
--media-brightness / --media-contrast   percent, default 100.0 each (software, global)
--stats
```
Startup guard: exits if none of `--media`, `--text`, `--web-port` given.
There is currently **no CLI flag for rotation/scale/position** — those
are runtime-only (state defaults 0°/100%/0/0, set from the web UI).

## Deployment

- `scripts/install-led-matrix.sh` — one-shot Pi setup: installs
  packages, disables onboard audio (shares PWM with GPIO18), creates
  `media-matrix.service` (systemd, runs `media_matrix.py` with flags from
  `/etc/default/media-matrix`) and `media-matrix-autoupdate.timer`/
  `.service` (polls `origin/<branch>` every 2 min via
  `scripts/auto-update.sh`, pulls + restarts on new commits).
- `scripts/auto-update.sh` — fetch/compare/`git pull --ff-only`/restart;
  includes a `git config --global --add safe.directory` guard since it
  runs as root via systemd against a repo likely cloned as a normal user.
- Autoupdate can be toggled at runtime from the web UI (`POST
  /autoupdate`), which just flips the systemd timer's enabled state.
- Normal update flow once installed: push to
  `claude/rp3-led-matrices-gff4ft` → autoupdate timer picks it up within
  ~2 min → service restarts automatically. Manual equivalent:
  `cd ~/lottesoft && git pull origin claude/rp3-led-matrices-gff4ft && sudo systemctl restart media-matrix`.
  A restart is only actually needed for changes that require a fresh
  process (flags file edits, code changes to non-live-reloaded logic);
  most `State` fields (brightness/contrast/rotation/scale/position/text/
  color/etc.) apply live through the web UI with no restart.

## Testing discipline used throughout

No hardware in the sandbox, so: stub only `rpi_ws281x` (the only Pi-only
import — a `PixelStrip`/`Color` stub is enough), and use the *real*
`numpy`/`Pillow`/`opencv-python-headless` for everything else. Every
change in this project was validated with a targeted script exercising
real image/video data and asserting on actual pixel content/shapes before
committing — not just `py_compile`. Keep doing this; it caught the
stacked-text clipping bug and confirmed the rotate/scale/position math
(a synthetic half-red test image made it easy to verify e.g. that a
`+10px` X offset shifts the red region by exactly 10 columns).

## Design principles established (keep following these)

1. **Never guess physical calibration in code — expose it as a live,
   independently-adjustable control instead.** Serpentine direction,
   panel rotation, per-panel layout, text travel direction vs. stacked
   layout vs. glyph rotation, media rotation/scale/position: all of these
   exist as separate runtime knobs because the "right" value can only be
   determined by looking at the actual hardware. When the user reports
   "X looks wrong on setting Y," the fix is almost always to decouple two
   things that were wrongly coupled, not to pick a different hardcoded
   default.
2. **Diagrams must be generated from the same code path that drives real
   output** (`render_wiring_svg`/`render_panel_svg` literally trace
   `build_index_map`), so they can never drift out of sync.
3. **Queue security invariant**: `/update` edits/removes existing queue
   items only; `/upload` is the only way to add one, and it validates
   file type. Don't relax this without the user asking explicitly.
4. **Validate with real media processing before every commit**, per the
   testing discipline above.
5. Keep the control page's client-side pattern: `state` JS object +
   `send()`/`sendDebounced()` POSTing to `/update`; server returns fresh
   HTML fragments (diagrams, queue rows) to splice in rather than doing
   full page reloads.

## Known gaps / likely next asks

- No automated test suite committed — all validation so far has been
  one-off scripts run in the sandbox per change, not checked in. Consider
  asking the user if they want a `tests/` dir with these made permanent,
  especially around `TextScroller` (4 direction×stacked combinations) and
  `transform_frame`.
- Rotation/scale/position are global-only (apply to the whole composited
  media frame), not per-queue-item like brightness/contrast is. If the
  user asks for per-item control here, follow the exact pattern already
  used for per-item `brightness`/`contrast` in queue items.
- No CLI flags exist for seeding rotation/scale/position at startup
  (only via the web UI at runtime) — add to `parse_args`/`State.__init__`
  the same way `--media-brightness` seeds `media_brightness`, if wanted.
- The user is mid-calibration of their physical panel setup (vertical
  layout, panel 1 rotated 180°, column serpentine mode). Expect more
  reports of "setting X visually does Y on my hardware, but I wanted Z" —
  treat these as real bugs/decoupling opportunities per the design
  principles above, not as "just recalibrate on your end."
- The wiring diagram (PSU terminal map, barrel jack power, resistor
  values) exists only as a previously-shared Claude Artifact, not a
  committed file. If asked to revise it, either ask the user for the
  artifact link or regenerate from the Hardware section above.
